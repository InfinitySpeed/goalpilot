# Native project workflow

N = scripts/native.py beside this skill's host.py. Build HERE; no nested agents/models.

FIRST tool command: python3 N begin --goal 'VERBATIM ORIGINAL GOAL' --repo REPO --run-dir RUN --context. RUN outside REPO. Forward requested --wall-seconds and --max-verifications; --goal-file accepts UTF-8. Do not reread this skill, scan files or run preliminary commands. Resume existing evidence with status/finish, never reset.

Begin supplies bounded context. NEXT command should implement, add focused native regressions, write criteria and deliver together. Extra reads only for named missing/truncated requirements/APIs. Preserve stack, existing tests/data/interfaces. Cover every workflow/guard; resolve reversible ambiguities. Aim <=2000 implementation+test tokens, correctness first. Use concise shared/table-driven logic; no speculative abstractions, duplicate transport tests, unrequested docs, narration or unchanged reruns.

Extract requested outcomes and constraints into 1–8 criteria quoting the original goal; do not turn anecdotes, hypotheses, or historical versions into acceptance criteria unless support for them is explicitly requested. Keep every check that directly verifies a requested outcome linked to its criterion. Broader suites and unavailable-environment checks may be included as `{"diagnostic":true}` checks: run and report them, but leave them unlinked so they do not gate directly verified criteria. Use `checks:[]` plus a blocker only for an explicitly required outcome that cannot be verified. Example: {"checks":[{"id":"focused","argv":["python3","check.py"]},{"id":"integration","argv":["python3","integration.py"],"diagnostic":true}],"criteria":[{"quote":"EXACT REQUESTED OUTCOME","checks":["focused"]}]}.
Use actual project commands and behavioral evidence, not compilation alone. Unverifiable criteria: checks:[] plus blocker. Save JSON and run python3 N deliver RUN --criteria-file CRITERIA in the SAME implementation command. It freezes commands/tests and runs the delivered suite once, retains the original snapshot, and separately checks only non-additive changed tests; this IS the test run. Repair concrete failures against the frozen acceptance. If a failed run reveals a missing direct check or a test file changed after delivery, amend with `amend RUN --criteria-file JSON --reason "specific verification gap"`; preserve all criterion quotes, retain passing evidence, and add required checks for every changed test file. Only a failed required check may be demoted to diagnostic. GoalPilot hashes the prior acceptance and attempts so no failure is lost. An amendment cannot change the original quoted goal, blockers, passing links, or existing checks; the SHA-256-checked acceptance history is retained and visible in `status`, and amendments are disallowed after success. Then finish. If the contract intentionally changes, use `finish --test-revision` as documented below. Stop at budget; status rejects stale results. No success claim without goal_complete:true. Authored tests do not prove independent semantic coverage. Final <=30 words of verified/missing/blocked facts.

For behavior that depends on execution context (working directory, environment, encoding, locale, platform, or process state), make the regression reproduce the exact transition and assert the requested observable value after it. Derive the expected value from the original request and existing public contract; a passing nearby or unchanged-context test does not cover it. For each criterion, check every named API path and every explicit error/result type, including clauses joined by “also”, “as well”, “both”, or “every”.

For user-facing file locations after the process working directory changes, ensure the emitted path still resolves for an editor launched from the original invocation context. Prefer absolute paths when the renderer otherwise makes relative paths resolve against the changed directory; assert the exact location line rather than only the basename.

Before claiming completion, run at least one focused test from every changed test file; a broad diagnostic suite cannot stand in for those checks. For invalid public inputs, test the exact documented exception type and use runtime validation errors rather than `assert`; when the request extends an existing validation rule “as well”, check each named path for consistent behavior.

If an identifier is rejected because it conflicts with a namespace separator, validate every explicitly named identifier that contributes to that namespace, not only the top-level name. Keep the existing test cases, update expected exception types only when the public contract is intentionally changed, and cover each affected path in the focused check.

When the request adds validation “as well” as an existing guard, do not leave the sibling guard implemented only by `assert`; use the same explicit runtime exception for both APIs and update the existing test case to assert that exception.

Allow at least two repair cycles (`--max-verifications 3` or more) for nontrivial changes; use 5 when several test files or behavior clauses are affected. Confirm every selected pytest node exists by checking the actual test definition or collected node ID before freezing acceptance. If the first verification fails only because a new test's expected output is wrong, fix the assertion against the actual documented format and rerun the same frozen acceptance; do not stop with a repairable failure.

When the relevant upstream test depends on an unavailable external service, reproduce the same request/response contract with a local server or deterministic mock and run it as the focused check. Keep the external integration suite reported as blocked; do not let that block erase a passing local behavior check or present it as a full-suite pass.

Link each criterion only to checks that directly verify its behavior. Mark a broader integration suite `diagnostic:true` when a focused offline test already proves the requested contract; it still runs and its result stays visible, but cannot turn that criterion green or red. Treat historical runtime details in an issue description as compatibility context unless the requested change explicitly requires support for that runtime, and never claim an unavailable runtime was tested.

If the goal intentionally changes behavior that an existing test asserts, revise that test in place, retain every named test case, and preserve its unrelated setup, transitions, and assertions. When a fixture becomes invalid under the new contract, migrate it while preserving equivalent behavior; do not flatten a nested case or drop surrounding coverage just to make it pass. Fix regressions in adjacent behavior unless the goal explicitly asks to change them. After the first verification records the draft, run `finish RUN --test-revision "specific contract change" --supersede-tests path/to/test_file`; repeat the flag for each affected original test file. GoalPilot archives the original bytes and rationale, runs the full revised suite, and still runs every other original test. Never use this for removing coverage or hiding unrelated failures; add/retain assertions for the new behavior.

For a full pytest suite that already fails in the frozen original source, GoalPilot may rerun that offline suite against the original source with the same frozen test set. It reports `no_new_pytest_failures` only when every candidate failure ID also failed on the original and no newly added or edited test case failed. Focused goal checks never receive this allowance. Review `baseline_adjusted_checks` and disclose every pre-existing failure in the final report. Goal-specific tests must pass; this does not turn a red project suite green.
